# AiDay 베타 운영 계획서 (Beta Operations Runbook)

> 2026-07-20 시작하는 초대형 컨시어지 베타의 **운영 런북**. "누구를·언제·어떻게·무엇으로 판정" 만 담는다.
> 지표 정의·목표치는 [PRODUCT-DECISIONS.md](./PRODUCT-DECISIONS.md), 계측 방법·SQL은 [beta-metrics.md](./beta-metrics.md),
> 실험 설계 근거는 [CEO 리뷰](./reviews/2026-07-19-ceo-review-web-beta-test.md)가 담당한다. 여기서 중복하지 않고 링크한다.

## 0. 한 줄 요약

공개 모집이 아니라 **초대된 12~15가구(준비 부족 시 6~8가구) 대상 7일 컨시어지 테스트**다. 목적은 기능 수요 조사가 아니라 세 가지 행동 가설 검증이다: ① 아침에 반복 확인하는가 ② 브리핑 때문에 실제 행동을 바꾸는가 ③ 다른 날씨 앱 재확인이 줄어드는가.

## 1. 참가자 모집·구성

- **모집 방식:** 공개 링크 배포 금지. 연락 가능한 지인·타깃 부모를 직접 초대한다.
- **표본 목표(연령군별 분리 — [PRODUCT-DECISIONS §3-6](./PRODUCT-DECISIONS.md)):**
  - 만 1~2세: 3~4가구
  - 만 3~6세: 6~7가구
  - 만 7~8세: 3~4가구
  - 합계 12~15가구. 모집이 부족하면 연령군 비율을 유지한 채 6~8가구로 줄인다.
- **기기 다양성:** iOS Safari와 Android Chrome을 **모두** 포함한다. iOS 웹 푸시 제약이 실재하므로 최소 iOS 3가구는 확보한다. 참가자별 기기·OS·브라우저를 운영 시트에 기록한다.
- **얇은 연령군은 배제하지 않고 "낮은 신뢰도"로 표시**한다(성숙도를 정직하게 드러내되 타깃에서 빼지 않음).
- **모집 현황은 운영 시트에 관리**한다(이 문서는 계획, 실시간 명단은 시트).

## 3. KPI — 무엇으로 판정하나 (통합)

지표가 세 곳에 흩어져 있어 여기서 **측정 원천별로 통합**한다. 원천이 다르면 준비물도 다르다.

| KPI | Go 기준 | 측정 원천 | 준비물 |
|-----|---------|----------|--------|
| **안전성** (치명적 안전 오류·진단/처방 단정) | **0건** | 저녁 폼 + 운영자 검토 | 폼 문항 + 매일 리포트 육안 점검 |
| 신뢰성 (브리핑 정상 생성률) | ≥ 97% | `report_error` / `report_viewed` | 계측(자동) |
| 반복 사용 (7일 중 아침 확인 3회+ 가구) | ≥ 50% | `session_start` (아침 05~10시) | 계측(자동) |
| 행동 변화 (옷차림·준비물·케어 중 1+ 실제 변경) | ≥ 50% | **저녁 폼** | 폼 필수 |
| 결과 적합 (저녁 응답 "적당했어요") | ≥ 70% | **저녁 폼** | 폼 필수 |
| 판단 대체 (다른 앱 재확인 없이 결정) | ≥ 80% | **저녁 폼** | 폼 필수 |
| 판단 품질 (수정 없이 쓸 수 있던 브리핑) | ≥ 80% | 저녁 폼 + 리포트 👍/👎 | 폼 + 계측 |
| 체크리스트 사용 (노출 세션 중 체크 1+) | ≥ 40% | `beta_checklist_interaction_daily` | 계측(자동) |
| 온보딩 완료율 (5단계) | ≥ 60% | `beta_onboarding_completion` | 계측(자동) |

**핵심: 절반은 계측으로 자동, 절반은 저녁 폼 없이는 측정 불가.** 저녁 폼을 안 걷으면 행동 변화·결과 적합·판단 대체를 영영 알 수 없다 — 이게 이 베타의 진짜 병목이다.

**7일 vs 14일 정합:** 위 "반복 사용 ≥50%"는 **7일 컨시어지 창의 Go 기준**이다. [PRODUCT-DECISIONS §1](./PRODUCT-DECISIONS.md)의 북극성 "아침 재방문율 ≥30%(14일 내 3일)"은 **베타 종료 후에도 계속 추적하는 장기 신호**로, `beta_morning_revisit` 뷰가 담당한다. 둘은 창이 다른 별개 지표이며 상충하지 않는다.

## 4. 저녁 피드백 폼 (외부 1분 폼 — 신설 필요)

인앱으로 측정 못 하는 행동·품질 KPI의 유일한 수집 수단. 구글폼 5문항 이내로 매일 저녁 발송.

1. 오늘 브리핑을 보고 **실제로 바꾼 것**이 있나요? (옷차림 / 준비물 / 케어 방식 / 없음 — 복수선택)
2. 오늘 브리핑 판단은 실제 날씨와 비교해 어땠나요? (적당했어요 / 과했어요 / 부족했어요)
3. 브리핑을 보고 **다른 날씨 앱을 또 확인**했나요? (아니오, 이걸로 충분 / 예, 재확인함)
4. 브리핑을 **그대로 쓸 수 있었나요, 아니면 머릿속으로 고쳤나요?** (그대로 / 일부 수정 / 많이 수정)
5. (자유) 오늘 가장 아쉬웠던 점 한 가지 — **아이 이름·질병명은 적지 마세요.**

> 인앱 "의견 보내기"·리포트 👍/👎와 별개 채널이다. 인앱은 상시 수거함, 저녁 폼은 KPI 판정 재료.

**저녁:** 폼 응답을 운영 시트에 누적. 👎·"부족/과함"·재확인 응답은 다음날 단톡방 질문이나 종료 인터뷰 후보로 표시.

**단톡방(참가 가구 오픈채팅):** 12~15가구 규모의 주 채널. 하루 1개 질문("오늘 옷차림 판단, 실제와 맞았나요?"). 로그가 *무엇을* 했는지 알려주면 단톡방은 *왜*를 알려준다.

## 7. 판정 기준 (베타 종료 시)

**즉시 중단(테스트 중):** 안전성 0건 기준을 깨면(치명적 안전 오류 또는 진단/처방 단정) 다른 지표와 무관하게 즉시 중단·수정. 롤백 URL 대기.

**종료 후 판정** — 위 KPI를 목표치와 대조해 `docs/reviews/`에 판정 문서 작성:

- **GO (다음 단계 착수):** 안전성 0건 + 반복 사용·행동 변화 둘 다 Go 기준 충족 + 신뢰성 ≥97%. → 자동 알림(웹 푸시/카카오) 착수 판단으로 이행.
- **ITERATE (재테스트):** 안전성은 통과했으나 반복 사용 또는 행동 변화가 미달. → 판단 품질·저녁 폼의 "아쉬운 점"을 근거로 골든 케이스·규칙 개선 후 재테스트. 알림 착수 보류.
- **STOP/RETHINK:** 안전성 위반 반복 또는 판단 대체 20%(재확인 80%+) → 가치 가설 자체 재검토.

> 수치는 업계 기준이 아니라 **다음 단계 착수용 내부 가설값**이다(CEO 리뷰). 표본이 작으므로 백분율을 과신하지 말고 저녁 폼 자유응답·인터뷰의 질적 신호와 함께 읽는다.

## 8. 이번 베타에서 제외 (스코프 컷)

PWA 설치·웹 푸시 자동화, 네이티브 앱, 카카오 API 자동 발송, 위젯·공동육아·OCR·커머스, 건강팁 확장·디자인 폴리싱, 테스트 중 P0 안전/데이터 오류가 아닌 기능 변경. 선제성 가설은 **사람이 매일 링크를 보내는 수동 운영**으로 검증한다.
