## 1. 성공 지표 (Success Metrics)

**검증하려는 가설:** "부모는 매일 아침, 환경 수치가 아니라 *우리 아이 기준으로 해석된 하루 첫 육아 판단*을 원한다." (MANIFESTO Core Truth)

| # | 지표 | 정의 | 목표 | 무엇을 검증하나 |
|---|------|------|------|----------------|
| 1 | 온보딩 완료율 | 가입 완료 → 온보딩 7단계 완료 비율 | ≥ 60% | 가치 제안이 프로필 입력 수고를 넘어서는가 |
| 2 | **아침 재방문율** ⭐ | 첫 방문 후 14일 내, 아침(05~10시 KST) 방문일 3일 이상인 사용자 비율 | ≥ 30% | **아침 판단 습관이 형성되는가 — 북극성 지표** |
| 3 | 체크리스트 인터랙션율 | AI 리포트가 노출된 세션 중 "오늘 챙길 것" 체크 1회 이상 발생 비율 | ≥ 40% | 리포트가 읽을거리가 아니라 *행동 가이드*로 쓰이는가 |

- 북극성은 **2번**이다. 1·3번은 2번이 안 나올 때 원인을 가르는 진단 지표다 (1 낮음 = 진입 문제, 3 낮음 = 리포트 품질 문제).
- **측정 수단:** PostHog 연동(SPEC Phase 5)이 선행 조건. 연동 전까지는 목표치를 판정하지 않는다 — 수치 없는 상태에서 감으로 판정하는 것을 금지.
- 지표는 3개를 유지한다. 추가하고 싶어지면 기존 것을 빼고 넣는다.

## 2. 출시 기준 (Definition of Done)

**"출시"의 정의:** 지인 테스트를 넘어 링크를 공개적으로 공유할 수 있는 상태 (공개 베타). 앱스토어·마케팅 이전 단계.

### 출시 차단 (Blocker) — 이것 없이는 공개하지 않는다

- [ ] **`/api/report` 보호** — 인증 또는 IP 레이트리밋. 호출당 Claude 비용이 발생하는 공개 엔드포인트는 어뷰즈 시 비용 사고로 직결
- [ ] **프로필 값 포맷 정규화 + 특이사항 매칭 버그 수정** — "우리 아이 맞춤"이 실프로필에서 실제로 작동해야 함. 현재는 데모 프로필에서만 우연히 작동 (별도 세션 진행 중)
- [ ] **홈 "시간대별 환경"·종합솔루션 실데이터 연동** — 카드에 "기상청·에어코리아 실측 데이터"를 명시하는데 판정 재료가 목데이터인 채 공개하는 것은 신뢰 훼손. `/api/weather`의 `hourlyForecast`가 이미 제공 중이라 UI 연결만 남음
- [ ] **이용약관·개인정보처리방침 실문서** — 아동 건강정보(민감정보)를 수집하므로 법적 차단 사항. 수집 근거·보존 기간·삭제 정책 포함
- [ ] **게스트 레이트리밋 적용** — 아래 결정 3-1의 구현
- [ ] **홈 "추천 아이템" 섹션 숨김** — 더미 가격의 쇼핑 카드는 MANIFESTO 안티패턴("쇼핑 추천 앱이 아니다")과 충돌하고 미완성 인상을 줌. 실연동 전까지 노출하지 않는다 (1줄 변경)
- [ ] **이메일 인증(Confirm email) 재활성화 + 커스텀 SMTP 연결** — 지인 테스트 기간 한정으로 인증을 임시 비활성화(2026-07-13 결정). 인증이 꺼진 상태로 공개하면 타인 이메일 선점 가입 → Google 계정 자동 연결(identity linking)을 통한 계정 탈취 경로가 열리므로, 공개 전 반드시 인증을 다시 켜고 커스텀 SMTP(Supabase 기본 메일은 시간당 2~4통 제한 + naver 도달률 낮음)를 연결한다. Site URL/Redirect URLs도 배포 도메인으로 설정

### 출시 후 개선 (Fast-follow) — 출시를 막지 않는다

1. **알림 발송 (당일 아침·전날 밤 브리핑 — 웹 푸시 + 카카오톡)** — 서비스의 핵심 약속이지만, 검증 가설(아침 판단의 가치)은 알림 없이도 지표 2로 측정 가능하므로 출시를 막지는 않는다. 단, 6주 고도화 계획([PRD.md](../PRD.md))에서는 발송 2종·카카오 채널까지 P0로 편성해 출시 직후 제공을 목표로 함 (2026-07-07 확장). 당일 아침을 중심에 둔 근거: 사전 가설검증 설문 수요 1위(당일 아침 자동 알림 76.5%, 13/17 — [원본](./validation/2026-05-사전-가설검증-설문.md)) + 판단 입력(당일 시간대별 예보)의 신선도 (채널·범위 결정: §3-3)
2. 환경정보 더미 섹션 3종 실데이터화 (야외활동 지수 / 시간대별 / 주간 날씨) + 새로고침 실동작
3. 위치 기반 자동 날씨 조회 (현재 좌표 4곳 하드코딩)
4. 오존 등급 계산, 꽃가루 잡초 카드 정리
5. 옷차림 착장 미리보기 실연동 (현재 고정 이미지)

## 3. 확정된 제품 결정 (구 "미정의" 항목)

SPEC.md에 "미정의 — 스펙 결정 필요"로 보류되어 있던 항목들을 아래와 같이 확정한다.

### 3-1. 게스트의 AI 리포트 호출 — **허용 + 레이트리밋**

- 게스트도 `/api/report` 실호출을 허용한다. "먼저 둘러볼게요" 경험이 곧 핵심 가치의 시연이므로, 차단하면 가입 전환의 가장 강한 근거를 스스로 없애는 셈.
- 대신 IP 기준 레이트리밋을 둔다 (기본값 제안: **일 10회/IP** — 데모 프로필 2개 × 재시도 여유. 구현 시 조정 가능).
- **게스트 → 가입 전환 시** localStorage 프로필을 DB로 이전한다 (가입·로그인 성공 직후 1회 업로드, 이후 DB가 원본).

### 3-2. 데모 프로필 표기 — **"예시" 뱃지 표시**

- 게스트 홈의 데모 프로필(지우·도윤)에 "예시" 뱃지를 표시해 실제 아이처럼 보이지 않게 한다.
- 사용자가 첫 실프로필을 등록하면 데모 프로필은 목록에서 제거한다.

### 3-3. 알림 1차 채널 — **웹 푸시 (PWA)** *(2026-07-07 변경 — 구 결정: 이메일)*

- N-01 파이프라인의 1차 채널은 **웹 푸시**로 한다. 선행 작업이던 PWA 전환(manifest + Service Worker)을 6주 고도화 범위([PRD.md](../PRD.md) P0 — 선제 알림)에 함께 편성해 부담을 해소했다. 외부 승인 없이 자급 구현이 가능하고, "홈 화면에 추가" 설치 경험이 리텐션에 유리하다.
- **이메일을 1차에서 제외한 사유:** 아침 준비 알림 특성상 도달·확인의 즉시성이 낮아 "먼저 알려주는" 약속에 부합하지 않음.
- 카카오톡 **"나에게 보내기"**(카카오 로그인 + talk_message)는 **P0로 승격한다** *(2026-07-07 2차 변경 — 구: P1)*. 근거: iOS 웹 푸시는 PWA 홈 화면 설치가 선행되어야 작동하므로, 웹 푸시 단독으로는 아이폰 사용자에게 "선제적으로 먼저 알려주는" 핵심 약속이 도달하지 않음. 선제 알림은 부가 기능이 아니라 서비스 본질의 전달 수단이라는 판단(PRD.md P0 참조). 온보딩의 카카오 연동 버튼은 실동작화한다.
- 카카오 알림톡(비즈메시지)은 발신프로필·템플릿 승인 리드타임 문제로 지표 2(아침 재방문) 검증 후 착수 — 기존 결정 유지 ("나에게 보내기"와 별개 채널).
- **일정 컨틴전시:** 카카오 채널(Phase 5)이 지연되면 공개 베타는 웹 푸시만으로 개시하고 카카오 채널은 베타 직후 첫 fast-follow로 이월한다.
- **(2026-07-12 착수 게이트 추가 — PRD v2.4)** "나에게 보내기"의 P0 지위는 유지하되 **무조건 구현하지 않는다.** 4주차 알림 퍼널 실측(PWA 설치율·권한 허용률)에서 iOS 도달 병목이 확인된 경우에만 Phase 5에 착수하고, 아니면 베타 직후 첫 fast-follow로 이월한다(해당 주는 골든 케이스 완성·판단 품질 개선에 투입). 채널 운용은 **사용자당 주 채널 1개 + 실패 시 폴백** — 아침·밤 × 2채널 중복 발송(하루 최대 4회)은 알림 피로를 만들므로 하지 않는다. 근거: 토큰 캡처·갱신·폐기·연동 해제·탈퇴 삭제까지 포함한 실제 구현 공수 재평가(Supabase는 프로바이더 토큰을 보관·갱신하지 않음) + 알림 피로 방지.

### 3-4. localStorage 네임스페이스 — **`aiday:`로 통일**

- 현재 `aiweather:`와 `aiday:`가 혼재. **`aiday:`로 통일**하고 기존 키는 1회성 마이그레이션(읽기 시 구키 발견 → 신키 복사 → 구키 삭제)으로 이전한다.
- 시점: 프로필 값 포맷 정규화 작업(진행 중)에 포함해 한 번에 처리한다 — 저장 스키마를 건드리는 작업을 두 번 하지 않기 위함.

### 3-5. 앱 형태 — **단계적 전환: PWA(P0) → 래퍼앱(P1) → 네이티브 재개발(Post-MVP)** *(2026-07-07 신설)*

- 최종 형태는 애플리케이션을 지향하되, 단계적으로 전환한다:
  1. **PWA (P0, 6주 내):** manifest + Service Worker — 설치 아이콘 + 웹 푸시. 외부 승인 없이 자급 구현 가능
  2. **래퍼앱 (P1):** WebView/Capacitor로 기존 웹앱을 감싸 앱스토어·플레이스토어 배포 + **네이티브 푸시(FCM/APNs)** — iOS 웹 푸시의 설치 제약을 근본 해소. 개발자 계정·스토어 심사 리드타임 때문에 6주 P0에서 제외
  3. **네이티브 재개발 (Post-MVP):** React Native/Flutter 등 — 공개 베타 검증(북극성 지표) 후 별도 결정
- 6주 내 iOS 도달 공백은 래퍼앱이 아니라 **카카오톡 "나에게 보내기" 채널(§3-3)**로 보완한다.

### 3-6. 연령 타깃 — **만 1~8세 전체 유지 + 연령군별 규칙·검증 분리** *(2026-07-12 신설 — PRD v2.7.2)*

- 핵심 타깃은 **만 1~8세 자녀를 둔 맞벌이 부모**다. 대표 페르소나(만 4세)는 사용 장면 구체화용 사례일 뿐 타깃을 제한하지 않는다.
- **v2.4의 "베타 모집 만 3~6세 우선" 결정을 폐기한다.** 판단 조건이 정형화된 연령대만 먼저 모집하면 전체 타깃이 사실상 축소되고, 다른 연령군의 정확도·수요를 검증하지 못한 채 확산 판단을 내리게 된다.
- **연령군별 규칙 세트 분리는 정확도를 위한 설계 결정이다.** 만 1세(유모차·체온조절)와 만 7세(도보·체육·자가 조절)는 판단 논리가 다르므로, 하나의 평균 규칙은 세 연령대 모두에게 어중간한 리포트를 낸다. 안전·예측 규칙과 액션 카탈로그를 **연령군(만 1~2·3~6·7~8) 키로 분리**하고, 규칙마다 적용 연령군·근거·버전을 기록한다.
- **검증은 전체 타깃을 축소하지 않고 표본만 연령층별로 나눈다.** 첫 7일 컨시어지 테스트 목표: 만 1~2세 3~4가구 · 만 3~6세 6~7가구 · 만 7~8세 3~4가구(총 12~15가구, 모집 상황에 따라 조정).
- **얇은 연령군은 배제하지 않고 낮은 신뢰도로 표시한다** — 성숙도를 정직하게 드러내되 타깃에서 빼지 않는다.
- **별도 To-Do:** 상한 만 8세 근거인 육아휴직 제도 연령 경계는 서비스 수요의 직접 인과로 단정하지 않는다 — 최신 법령 확인 + 만 7~8세 부모 사용자 조사를 별도 수행한다.
- 상세: [PRD.md](../PRD.md) §04(연령별 판단 규칙)·§05(입력 축·골든 케이스)·§08(연령군별 규칙 세트).
