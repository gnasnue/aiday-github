# 아이데이(AiDay) 문제정의 프레임워크 v2

> **기준 축 (절대 원칙):** 아이데이는 '외출 준비 도우미'가 아니다. 부모의 하루 육아 의사결정이 시작되는 **첫 판단** — 오늘의 환경정보를 내 아이 기준으로 해석해 옷차림·준비물·오늘 하루의 케어 방식을 결정하는 일 — 을 지원하는 서비스다. 이 포지셔닝은 모든 문서·피치·기능 설계에서 흔들리지 않는다.

---

## 1. 고객의 입장에서 생각한다: 디자인 싱킹

**질문: 아이데이 고객(만 1~8세 자녀를 둔 맞벌이 부모)은 어느 순간, 어디서 가장 불편해하는가?**

매일 아침, 하루가 시작되는 순간이다. 부모의 하루 육아는 "오늘은 어떤 날인가, 그래서 내 아이에게 뭐가 필요한가"라는 판단에서 시작된다. 기온·미세먼지·꽃가루를 확인하고, 아이의 컨디션과 오늘 일정을 떠올리며, 옷차림·준비물·오늘의 케어 방향을 결정해야 한다.

문제는 이 첫 판단이 하필 출근·등원 준비가 겹치는 가장 바쁜 시간대에, 매일, 처음부터 다시 수행되어야 한다는 것이다.

더 깊은 문제는 **이 판단이 불완전한 입력값으로 이루어질 수밖에 없는 구조**라는 점이다(→ 8번 페르소나 참조). 판단에 필요한 입력값은 '현재 날씨' 하나가 아니라 '오늘 하루의 시간대별 환경 궤적 × 아이의 일정 × 아이의 체질'인데, 바쁜 아침에 이 결합을 수행할 인지 여력이 없다. 서연 씨처럼 정보를 확인하고 합리적으로 판단해도, 입력값이 축소된 판단은 케어 공백(땀 젖음·추위)으로 이어진다.

불편의 본질은 정보 부족이 아니라 **하루의 첫 육아 판단이 통째로 부모의 머릿속에서만, 불완전한 입력값으로 이루어진다는 구조**다. 사전 가설검증 설문(2026-05, 온라인, n=17 — [원본](validation/2026-05-사전-가설검증-설문.md))에서 88.2%(15/17)는 정보 탐색에 하루 10분 이내(64.7%는 1~3분)만 쓸 수 있다고 답했고, 옷차림 결정이 어려운 상황 1위는 "일교차가 큰 환절기"(82.4%, 14/17)였다 — 탐색 시간은 구조적으로 부족한데 판단 대상은 시간대별 변화라는, 페르소나 시나리오와 정확히 일치하는 구조다.

## 2. 이 문제가 (고객의) 무엇을 해결하려고 하나: JTBD

**질문: 부모가 아이데이를 고용해서 하려는 진짜 일은 무엇인가?**

- **기능적 Job:** "오늘 하루 내 아이를 어떻게 케어할지, 하루의 첫 판단을 빠르고 정확하게 끝내고 싶다." 정보 확인이 아니라 **판단의 완료**가 Job이다. 옷차림·준비물은 그 판단의 출력물이다. 그리고 '정확하게'의 기준은 지금 이 순간이 아니라 **오늘 하루 전체**다(등원 순간이 아니라 산책 시간의 28도, 하원 시간의 17도까지).
- **감정적 Job:** "내가 뭘 놓쳐서 아이가 고생하는 일이 없기를." 잘못된 판단(얇게 입혀 감기, 마스크 누락)에 대한 불안, 그리고 실패 후 따라오는 죄책감의 해소. 페르소나 시나리오의 종착점이 '감기'가 아니라 '죄책감'이라는 점이 이 Job의 무게를 보여준다.
- **사회적 Job:** "바쁘지만 아이를 세심하게 챙기는 부모이고 싶다."

핵심 통찰: 부모가 고용하는 것은 '날씨 해석기'가 아니라 **'하루 육아의 첫 판단을 함께 내려주는 파트너'**다. 이 Job은 외출 여부와 무관하게 매일 발생한다 — 외출하지 않는 날에도 "실내 습도 관리, 환기 시점, 피부 케어"라는 판단은 필요하다.

## 3. 문제를 해체한다: 제1원리 사고

**질문: '원래 그래왔으니까' 남아있는 가정은 무엇인가?**

- **"환경 정보의 해석은 부모가 한다"** → 왜? 해석·판단의 주체가 사람이어야 할 이유는 없다. AI가 아이 컨텍스트를 알면 판단까지 제공 가능하다.
- **"옷차림 판단의 기준은 현재 날씨다"** → 페르소나 시나리오가 반증. 판단의 정답은 현재가 아니라 **하루의 시간대별 환경 궤적과 아이 일정의 교차점**(산책 시간의 기온, 하원 시간의 기온)에 있다. 날씨 앱에 시간대별 예보가 '존재'하는 것과, 바쁜 아침에 그것을 아이 일정과 '결합'하는 것은 전혀 다른 문제다.
- **"육아 앱 = 기록(tracking) 도구"** → 신생아기의 관성. 유아기 이후 부모의 매일의 Job은 기록이 아니라 판단이다.
- **"매일의 판단은 매일 새로 해야 한다"** → 입력값(환경)은 매일 바뀌지만, 판단의 틀(내 아이의 특성·성향·과거 반응)은 누적 가능하다. 누적하면 판단은 점점 자동화된다 → Family Memory의 존재 이유.
- **"AI에게 물으려면 매번 상황을 설명해야 한다"** → 메모리가 있으면 불필요하다. 묻기 전에 먼저 제안할 수도 있다.
- **"아침은 원래 정신없는 것"** → 첫 판단이 대행되면, 부모에게는 확인과 실행만 남는다.

## 4. 문제의 원인을 끝까지 추적한다: 5 Why

**질문: '하루의 첫 육아 판단'이 매일 반복되는 인지 부담이 되는 근본 원인까지 알아냈는가?**

**출발 현상:** 부모의 하루 육아는 매일 아침 '오늘의 환경을 내 아이 기준으로 판단하는 일'에서 시작되는데, 이 첫 판단이 가장 바쁜 시간대에 매일 처음부터 다시 수행되며 지속적인 인지 부담이 된다. 입력값이 축소된 채 이루어진 판단은 케어 공백으로 이어지기도 한다. (예: 현재 기온에 맞춰 입혔는데 일교차로 아이가 땀에 젖고 추위에 떪 — 8번 페르소나)

1. **왜 이 첫 판단이 매일 부담인가?**
   → 출근·등원 준비가 겹치는 가장 바쁜 시간대에, 여러 변수를 종합하는 판단을 수행해야 해서. 여력이 없으니 가장 접근하기 쉬운 입력값(현재 날씨) 하나로 판단이 축소된다.
2. **왜 이 판단은 미리 해둘 수 없고 매일 다시 해야 하나?**
   → 판단의 입력값(기온·일교차·미세먼지·꽃가루·아이의 당일 컨디션)이 매일 바뀌는 당일 변수라서. 어제의 결론을 재사용할 수 없다.
3. **왜 판단에 인지 자원이 많이 드나?**
   → 필요한 입력값이 4개 축(시간대별 환경 궤적 / 아이 체질·건강 / 아이의 오늘 일정 / 준비물·케어 옵션)에 걸쳐 있고, 환경 정보는 여러 앱에 파편화되어 있으며, 이를 결합하는 작업이 온전히 부모의 머릿속에서 이루어져서.
4. **왜 이 결합을 부모가 직접 해야 하나?**
   → 어떤 서비스도 '내 아이'를 모르기 때문에. 정보 앱은 일반 데이터만 제공하고(시간대별 예보는 있지만 아이 일정과 교차시켜 주지 않음), 생성형 AI는 매번 아이 상황을 재설명해야 한다.
5. **왜 어떤 서비스도 내 아이를 모르나?**
   → 아이의 특성·이력·반응을 저장하고 환경 데이터와 결합해 추론하는 구조(Family Memory + Contextual Reasoning)가 시장에 없어서.

**→ 근본 원인: 매일 새로 발생하는 '하루의 첫 육아 판단'을 내 아이 기준으로 수행해 줄 구조의 부재.**

*솔루션은 이 사슬을 역순으로 끊는다: 5번→Family Memory, 4번→자녀 프로파일 + 생활패턴 등록, 3번→시간대별 환경×일정 통합 브리핑, 2번→매일 선제 알림, 1번→"판단은 끝나 있고 확인만 하는 아침".*

## 5. 업무 프로세스를 재정의: 시스템적 사고

**질문: '하루의 첫 육아 판단' 전체를 AI가 대체한다면 프로세스를 어떻게 다시 그릴까?**

**기존 프로세스 (페르소나의 실제 아침):**
기상 → 날씨 앱에서 현재 기온 확인 → (시간대별 예보·일교차는 확인 못 함) → (머릿속) 현재 기온 기준 옷차림 결정 → 등원 → *11시 산책: 28도, 땀 흠뻑* → *17시 하원: 17도, 추위* → 케어 공백 → 죄책감.
판단 단계 전부가 부모 몫이며, 시간 압박으로 입력값이 축소되고, 매일 리셋된다.

**재설계 프로세스 (아이데이):**
(기상 전) AI가 시간대별 환경 예보 × 아이 프로파일(체질·건강) × 아이 일정(등원·산책·하원) × Family Memory로 판단 완료 → 아침 브리핑 선제 발송 → 부모는 **확인 + 예외 수정만** → 실행 → 수용/거부·결과 피드백이 메모리에 누적 → 다음 일교차 날엔 판단이 더 정확해짐.

구조적 전환은 두 가지다.
1. "부모가 묻고 AI가 답한다" → **"AI가 먼저 제안하고 부모가 승인한다"** (Phase 2 선제 알림이 기능 추가가 아니라 프로세스 재정의인 이유)
2. 기존 프로세스는 매일 리셋되지만, 재설계 프로세스는 **매일의 판단이 자산으로 누적**된다 (Family Memory가 해자인 이유)

## 6. 마지막 점검: 문제해결의 증명

**질문: 내가 푼 문제가 KPI를 실제로 움직이나?**

측정 대상은 "외출 준비가 편해졌나"가 아니라 **"하루의 첫 육아 판단이 아이데이로 대체되었나"**이다.

| 지표 | 정의 | 검증하는 것 |
|---|---|---|
| **판단 대체율** (북극성 후보) | 아침 브리핑 확인 후 추가 정보 탐색 없이 판단을 종료한 비율 | 판단 대행이 실제로 작동하는가. 사전 설문 기준선(88.2%가 하루 10분 이내 정보 탐색) 대비 탐색 시간 감소 |
| **아침 시간대 오픈율 / 주중 DAU·WAU** | 6~9시 브리핑 확인율, 주중 재방문 | '매일의 첫 판단'이라는 Job 정의의 실증 |
| **외출 없는 날 리텐션** | 주말·방학·우천일의 사용 유지율 | **"외출 앱이 아니라 데일리 케어 판단 앱"이라는 포지셔닝의 데이터 증명** — 이 지표가 유지되면 포지셔닝 주장을 말이 아니라 데이터로 방어 가능 |
| **추천 수용률** | 브리핑 내 액션별 수용/거부 로그 | KPI인 동시에 Family Memory의 학습 데이터 |
| **개인화 체감 (수용률 기울기)** | 사용 4주 차 수용률 vs 1주 차 수용률 | "쓸수록 정확해진다" = 해자 주장의 정량 실증 |
| **실패 회피 사례** | "브리핑 덕에 여벌 옷을 챙겨서 유용했다" 류의 정성 피드백 수집 | 페르소나 시나리오형 실패의 감소 (정성 지표, 베타 인터뷰로 수집) |

## 7. AI를 위한 프롬프트 생성

**질문: AI가 이 문제를 풀게 하려면 어떻게 PRD를 생성하라고 할까?**

1~6의 산출물과 8번 페르소나를 입력으로 한 PRD 생성 프롬프트 골격:

> 너는 시니어 PM이다. 다음 컨텍스트를 바탕으로 '데일리 케어 브리핑(하루의 첫 육아 판단 대행)' 기능의 PRD를 작성하라.
>
> **[서비스 정의]** 이 기능은 외출 준비 도우미가 아니다. 부모의 하루 육아 의사결정의 첫 스타트 — 환경정보를 내 아이 기준으로 해석해 옷차림·준비물·오늘의 케어 방식을 판단하는 일 — 을 대행한다. 외출하지 않는 날에도 브리핑은 유효해야 한다(실내 케어 가이드 포함).
>
> **[판단 스펙]** 판단의 입력은 4개 축이다: ① 시간대별 환경 궤적(기온·일교차·미세먼지·꽃가루·자외선·습도), ② 아이 프로파일(연령·체질·건강상태), ③ 아이의 오늘 일정(등원·산책·하원 등 시간대별), ④ Family Memory(과거 추천 수용/거부, 반응 이력). 판단 기준 시점은 '현재'가 아니라 '오늘 하루 전체'이며, ①과 ③의 교차점(예: 산책 시간대의 기온)을 반드시 평가한다.
>
> **[고객 불편 순간=1번] [JTBD=2번] [근본 원인 사슬=4번] [재설계 프로세스=5번] [성공 지표=6번] [대표 페르소나·시나리오=8번]**
>
> **포함 항목:** 유저 스토리(외출일/비외출일 각각), 엣지케이스(폭염·한파 경보, 일교차 10도 이상, API 장애 시 Fallback Chain, 아이 컨디션 급변, 일정 변경), 안전 요구사항(절대 안전 기준은 규칙 기반 레이어로 LLM 판단에 선행, 의학적 표현 차단 필터), 수용 기준, 수용/거부 피드백의 메모리 반영 스펙.
>
> **테스트 케이스로 8번 페르소나 시나리오를 포함하라:** 입력(만 4세, 땀 많은 체질, 등원 8:30/산책 11~12시/하원 17시, 예보 20°→28°→17°)에 대해 출력이 [겹쳐 입기 + 여벌 옷 + 땀 케어 포인트]를 포함해야 통과.

## 8. 대표 유저 페르소나: "서연" (상세)

> 이 페르소나는 가상의 대표 인물이며, 사전 설문 응답 패턴(일교차 어려움 82.4%, 탐색 가용 시간 하루 10분 이내 88.2%)과 실사용 시나리오를 결합해 구성했다. 판단 엔진의 표준 테스트 케이스이자, 피치의 Before/After 스토리 원형으로 사용한다.

### 8-1. 프로필

| 항목 | 내용 |
|---|---|
| 이름 (가칭) | 김서연 |
| 연령/직업 | 30대 중반, 맞벌이 직장인 여성 |
| 가족 | 배우자(맞벌이), 만 4세 자녀 "지우" |
| 자녀 특성 | **땀이 많은 체질.** 활동량 많음. 어린이집 재원 중 |
| 자녀 일정 | 등원 8:30 / 어린이집 산책(야외활동) 11:00~12:00 / 하원 17:00 |
| 정보 습관 | 아침에 날씨 앱으로 '현재 기온'만 확인 (시간대별 예보를 뜯어볼 여력 없음) |
| 핵심 감정 | 아이를 세심히 챙기고 싶은 마음 vs 시간 부족. 케어 실패 시 강한 죄책감 |

### 8-2. Before: 아이데이가 없는 하루 (실패 시나리오)

| 시각 | 상황 | 서연의 판단/상태 |
|---|---|---|
| 07:00~08:20 | 출근 준비 + 등원 준비 동시 수행. 정신없음 | 날씨 앱을 열어 **현재 기온 20도** 확인 |
| 08:20 | 옷차림 결정 | 20도 기준으로 합리적 선택: **면 티셔츠 + 긴 바지.** 시간대별 예보·일교차는 확인하지 못함 |
| 08:30 | 등원 | 판단 종료. 이 시점에서는 아무 문제 없어 보임 |
| 11:00~12:00 | 어린이집 산책. **기온 28도까지 상승** | 땀 많은 체질의 지우, **땀에 흠뻑 젖음.** 여벌 옷 없음 |
| 17:00 | 하원. **기온 17도로 급강하 (일교차 11도)** | 땀에 젖었던 지우가 추위에 떪 |
| 저녁~ | 지우 컨디션 저하, 감기 기운 | 서연: **"내가 꼼꼼히 못 챙겨서…"라는 죄책감** |

**이 시나리오의 전략적 핵심: 서연은 아무것도 게을리하지 않았다.** 정보를 확인했고(탐색 수행), 확인한 정보 기준으로는 합리적으로 판단했다(20도→면 티셔츠는 틀린 선택이 아님). 그런데도 실패했다. 실패의 원인은 부모의 노력 부족이 아니라 **판단 구조의 결함**이다 — 이것이 "문제는 정보가 아니라 판단"이라는 아이데이 명제를 구체화한 **대표 검증 시나리오**다. 다만 가상 시나리오이므로 그 자체가 증거는 아니다 — 명제의 실증은 베타의 행동 지표(판단 대체율·아침 재방문·결과 적합률)가 담당한다.

### 8-3. 실패의 해부: 판단에 필요했던 입력 4개 중 3개가 누락

| 필요했던 입력 | 실제 상황 | 누락의 결과 |
|---|---|---|
| 현재 기온 (20도) | ✅ 확인함 | 이것 '하나만으로' 판단이 이루어짐 |
| **시간대별 예보** (11시 28° / 17시 17°, 일교차 11도) | ❌ 날씨 앱에 존재하지만, 바쁜 아침에 시간대별로 확인·해석할 인지 여력 없음 | 산책 시간의 더위, 하원 시간의 추위 예측 실패 |
| **아이 체질** (땀 많음) | ❌ 어떤 앱도 모름. 서연의 머릿속에만 있으나 아침엔 환경 정보와 결합할 여력 없음 | "땀 젖음 → 젖은 옷 → 체온 급강하" 리스크 미반영 |
| **아이의 오늘 일정** (11~12시 산책, 17시 하원) | ❌ 어떤 앱도 모름 | 판단 기준 시점이 '등원 순간'에 고정. 정작 리스크는 산책·하원 시점에 발생 |

→ **판단의 정답은 "지금 날씨에 맞는 옷"이 아니라 "시간대별 환경 궤적 × 아이 일정 × 아이 체질"의 함수**다. 판단의 시간 단위는 '현재'가 아니라 '오늘 하루 전체'다. 이것이 서비스 본질이 '외출 준비'가 아니라 '하루 케어 방식의 첫 판단'인 이유이며, 데이터 레이어 고도화(정적 API → 시계열 예보)가 최우선 과제인 이유다.

### 8-4. After: 아이데이가 있는 같은 하루

**07:10, 선제 브리핑 (웹 푸시 — 채널 명세는 PRD P0 발송 참조):**

> 서연 님, 오늘은 **일교차가 큰 날**이에요. (등원 20° → 산책시간 28° → 하원 17°)
> 지우는 땀이 많은 체질이라 오늘 같은 날 특히 주의가 필요해요.
>
> ☑ **얇은 반팔 + 가벼운 겉옷** — 산책 때 벗고, 하원 때 입혀요
> ☑ **여벌 티셔츠 1장** — 산책 후 땀에 젖으면 갈아입도록 가방에
> ☑ 알림장 한 줄: "산책 후 옷 갈아입혀 주세요"
>
> 오늘의 케어 포인트: 땀 흘린 뒤 체온 급강하 주의

| 시각 | Before | After |
|---|---|---|
| 07:10 | (판단 시작 전) | **판단이 이미 완료된 채 도착.** 서연은 확인만 |
| 08:20 | 현재 기온만으로 판단 | 겹쳐 입기 + 여벌 옷 + 알림장 메모 실행 (1분) |
| 11~12시 | 땀에 흠뻑 젖음 | 산책 때 겉옷 벗김. 산책 후 여벌 옷으로 교체 |
| 17:00 | 젖은 옷 + 17도 = 추위 | 겉옷 착용, 마른 옷 상태로 하원 |
| 저녁 | 감기 기운 + 죄책감 | 지우 컨디션 양호. 서연: **"챙겨줬다"는 안도감.** 브리핑에 '여벌 옷 유용했어요' 피드백 → Family Memory에 누적 |
| 다음 일교차 날 | (동일한 실패 반복 위험) | **지우의 반응 이력이 반영된 더 정확한 브리핑** |

### 8-5. 이 페르소나에서 도출되는 요구사항 (제품 스펙 연결)

1. **시계열 환경 데이터 필수** — 현재값이 아닌 시간대별 예보(기온·일교차·미세먼지·꽃가루·자외선·습도)가 판단 입력. (기술서 데이터 레이어 1개월차 고도화 항목의 근거)
2. **생활패턴(일정) 프로파일** — 등원·산책·하원 등 시간대별 일정을 온보딩에서 등록. 환경 궤적과 일정의 **교차점 평가**가 판단 엔진의 핵심 로직.
3. **체질·건강 특성의 판단 반영** — '땀 많음' 같은 체질 태그가 리스크 시나리오(땀→젖은 옷→체온 저하)로 연결되는 추론 규칙. CoT 추론 단계에 "아이 특성 → 위험 우선순위" 명시.
4. **실행 가능한 액션 단위 출력** — "겹쳐 입히세요"가 아니라 [반팔+겉옷 / 여벌 옷 1장 / 알림장 문구]처럼 즉시 실행 가능한 체크리스트.
5. **피드백 루프** — 액션별 수용/거부 + 결과 피드백("유용했어요")이 Family Memory에 축적되어 다음 판단의 입력이 됨.
6. **판단 엔진 표준 테스트 케이스** — 입력: (만 4세, 땀 많은 체질, 등원 8:30/산책 11~12시/하원 17시, 예보 20°→28°→17°) → 기대 출력: 겹쳐 입기 + 여벌 옷 + 땀 케어 포인트 포함 시 통과. 회귀 테스트로 상시 운용.

### 8-6. 사용 시 주의 (안전·표현)

- 공식 문서·서비스 화면에서 **"감기를 예방해 준다" 등 건강 결과를 약속하는 표현 금지.** 의료적 기대·책임 문제가 발생하며, 이는 안전 레이어(의학적 표현 차단 필터)가 막기로 한 바로 그 영역이다.
- Before 시나리오의 종착점은 "아이가 추워하며 하원했고, 부모는 죄책감을 느꼈다"까지 기술한다. '감기'는 부모 인터뷰 인용 등 실제 경험담 톤으로만 처리한다.
- After의 가치 서술은 "판단을 대신해 주고, 놓침을 줄여 준다"로 한정한다.
