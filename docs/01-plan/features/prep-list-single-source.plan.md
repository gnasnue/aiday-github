- **작성일:** 2026-07-27
- **선행 계획:** `checklist-today-decision.plan.md` (설계 SUPERSEDED, 제품 결정·검증된 사실은 유효)
- **결정 근거:** 엔지니어링 리뷰 D11 — Codex P0 3건이 전부 "소스가 둘이라서" 발생. 합집합 봉합은 성립하지 않음(코드로 확인)
- **제품 결정(유효):** 체크리스트는 "오늘 달라진 것"이다. 무난한 날은 0~1개. **지표 정의를 같은 PR에서 함께 바꾼다**

## 0. 한 줄 요약

준비물 목록(체크리스트 + 케어 플랜 칩)을 **규칙 엔진 한 곳**에서 만들고, AI는 **그 목록을 설명·우선순위화**한다. AI는 더 이상 물건 이름을 만들지 않는다.

---

## 1. 왜 이 방향인가

### 근거는 이미 이 프로젝트 안에 있다

2026-07-20 제품 결정이 케어 플랜 칩 엔진을 규칙으로 확정할 때 쓴 A/B 데이터(`scripts/chip-ab.test.ts`, 48슬롯):

| 축 | 규칙 | AI |
|---|---:|---:|
| 커버리지 갭 | **0** | 10 |
| 결정성(같은 입력 → 같은 출력) | **0 흔들림** | 7슬롯 흔들림 |

"빠짐없이·흔들림 없이 보여야 하는 목록"이라는 표면에서는 규칙이 이긴다. 체크리스트도 **같은 종류의 표면**인데, 그 결론을 목록에 적용하지 않고 있었을 뿐이다.

### 소스가 둘이면 봉합이 불가능하다 (코드로 확인)

| 깨진 전제 | 검증 |
|---|---|
| 합집합이 `0~4개` 계약과 양립 | **거짓** — `lib/prep.ts:121` `.slice(0,2)` × 슬롯 4개 = 최대 8개. 4개로 자르면 `칩 ⊆ 체크리스트`가 깨진다 |
| `heroSt === "caution"`이 안전 게이트 | **거짓** — `issues` 후보에 폭염·기온이 없다(`lib/hero-brief.ts:374` 주석 명시). 34°C 맑은 날은 `normal` |
| 두 엔진이 무난한 날 모두 0개 | **거짓** — `lib/prep.ts:104` 피부 민감 아이는 날씨 무난해도 보습제 |

## 2. 구조 — 지금 vs 새로

```
【지금 — 소스 3갈래】

  AI ──▶ checklist(문자열 "😷 마스크")  ──▶ 오늘 챙길 것
     └─▶ prep(슬롯별 키워드)  ··· 화면 미사용(PR #174)

  규칙 buildPrepKeywords ─────────────▶ 케어 플랜 칩
  규칙 buildRecommendation ───────────▶ 폴백 체크리스트
                                          ▲
                        AI 실패·빈 목록이면 여기로 (판정 4곳에 흩어짐)


【새로 — 소스 1개】

  weather/air/uv/pollen + child ──┐
                                  ▼
                    buildTimeline(schedule, env)      ← 서버에서 호출 가능(§3.1 확인)
                                  ▼
                    ┌─────────────────────────────┐
                    │  buildPrepPlan()  (신설)     │  하루 목록 + 슬롯 배치를
                    │  · 아이템 = 규칙 단일 소스   │  한 곳에서 함께 결정
                    │  · 상한·우선순위 한 곳       │
                    │  · 마스크·연령 정책 적용     │
                    └──────────┬──────────┬───────┘
                               │          │
                     items[](하루)   bySlot(슬롯별)
                               │          │
                               ▼          ▼
                        오늘 챙길 것   케어 플랜 칩     ← 같은 소스라 ⊆ 자동 성립
                               │
                               ├──▶ Claude 입력("오늘 목록: 우산, 여벌 상의")
                               │         ▼
                               │    hook · message (설명·우선순위·형태·타이밍·위임)
                               ▼
                        응답에 items 동봉 ──▶ prep_count 계측(타이밍 문제 소멸)
```

## 3. 핵심 설계

### 3.1 서버가 목록을 만든다 — 실현 가능성 확인

`buildTimeline(schedule, env)`은 `EnvRaw`에 대한 **순수 함수**(`lib/timeline.ts:201`)이고, `/api/report`는 클라이언트가 보내는 `weather`·`air`·`uv`·`pollen`·`child.schedule`을 이미 받는다. `air`는 `/api/air`가 반환한 객체를 그대로 전달하므로 **`air.hourly`(시각별 pm10 실측)까지 포함**한다(`app/api/air/route.ts:83`, `page.tsx:765`).

→ 서버는 클라이언트와 **동일한 입력**으로 타임라인과 규칙 목록을 계산할 수 있다. 별도 입력 확장이 필요 없다.

### 3.2 `buildPrepPlan()` 신설 — 목록과 슬롯 배치를 함께 결정

`lib/prep-plan.ts`(신설)에 순수 함수를 둔다.

```
buildPrepPlan({ slots, profile, maskAllowed }) → {
  items: PrepItem[]        // 하루 목록 (0~4개, 우선순위 정렬)
  bySlot: Record<슬롯, PrepItem[]>   // 칩 (items의 부분집합)
  dropped: PrepItem[]      // 상한에 걸려 빠진 것 (관측용)
}
```

**상한을 한 곳에서 정한다.** 지금 상한이 두 곳(칩 슬롯당 2개 / 체크리스트 3~4개)에 흩어져 충돌한다. `items`는 우선순위 상위 **최대 4개**, `bySlot`은 `items` 안에서만 고른다 → `bySlot ⊆ items`가 **구조적으로** 성립한다(런타임 검사가 아니라 타입·구성으로).

`dropped`를 남기는 이유: 상한에 걸려 빠진 준비물이 있으면 조용히 사라지지 않고 관측된다(무언의 절단 금지).

**기존 규칙 로직은 재사용한다.** `buildPrepKeywords`의 조건·임계값·우선순위를 그대로 옮기고(이미 `isSweatWeather`·`canRecommendMask`·`canonicalPrep` 단일 소스를 쓴다), `buildRecommendation`의 체크리스트 생성부는 이 함수로 대체한다. **새 규칙을 만들지 않는다** — 이번 변경은 소스를 하나로 모으는 것이고, 판정 기준을 바꾸는 것이 아니다.

### 3.3 AI 출력 스키마 — `checklist`·`prep` 제거

```
지금: { hook, message, checklist, prep }
새로: { hook, message }
```

AI는 물건 이름을 만들지 않는다. 프롬프트는 목록을 **입력**으로 받고, hook·message에서 그것을 설명·우선순위화한다. v25가 세운 message 3문장 구조(판단 / 이 아이의 근거 / 실행)와 실행 디테일(형태·수량·타이밍·위임)은 **그대로 유지**한다 — 그게 AI가 잘하는 부분이고, 목록 생성이 아니라 설명이다.

**AI가 목록에 없는 물건을 말하면?** 프롬프트로 금지하고, eval에서 결정적으로 검사한다(`hook·message의 준비물 ⊆ items`). 지금은 반대 방향(`hook ⊆ checklist`)으로 검사하는데, 진실원이 바뀌므로 기준도 바뀐다.

### 3.4 폴백이 단순해진다

목록은 **AI와 무관하게** 항상 있다. AI가 실패하면 `hook`·`message`만 규칙 문장으로 폴백하고, 목록은 그대로 보인다.

→ 체크리스트 길이를 성공 신호로 쓰는 4곳(`691`·`859`·`971`·`1111`)이 **전부 사라진다.** 선행 계획의 C2(폴백 판정 분리)가 불필요해진다. Codex P1(추출 경계가 잘못됐다)도 함께 해소된다 — 나눌 판정 자체가 없어진다.

### 3.5 무난한 날 0개가 결정이 된다

규칙이 조건부이므로 무난한 날은 자연히 0개다. **단, 피부 민감 아이의 상시 보습제처럼 체질 기반 항목은 남는다** — 그건 오작동이 아니라 그 아이에게 사실이고, message가 이유를 설명한다. "무난한 날 = 항상 0개"가 아니라 "무난한 날 = 규칙이 트리거한 것만"이 정확한 표현이다.

### 3.6 지표 계측의 타이밍 문제가 소멸한다

목록이 **서버 응답에 동봉**되므로 `track("report_viewed")` 시점(`page.tsx:927`)에 개수를 이미 알고 있다. 새 이벤트도, 렌더 시점 발화도, 중복 방지 ref도 필요 없다.

→ Codex P1-9(계측 시점)와 선행 계획 D7이 함께 해소된다. `report_viewed` props에 `prep_count`만 추가한다.

**선글라스는 구성원에서 제외한다.** WHO 복합 보호 지침(모자·선글라스·선크림)은 일반 인구 대상이고, 유아 UV 선글라스는 보유율이 낮아 "없는 물건을 챙기라"는 항목이 된다. 마스크처럼 연령 게이트가 추가로 필요해지는 것도 이유다. `모자 · 선크림` 2개가 실행 가능한 최소 세트다.

**`물통`은 이름을 바꾸지 않는다.** `수분 보충`은 물건이 아니라 목적이고, 그 구분은 이미 코드에 있다(`lib/item-recommend.ts:49` — `물병/물통`이 이름, `수분 보충`이 note). 이름 자리에 목적어를 넣으면 위계가 무너지고, 같은 어휘를 공유하는 케어 플랜 칩에 동사형 칩("물 챙기기")만 튀어 PR #175의 어휘 정렬이 다시 갈린다. 이유는 목록이 아니라 message가 말한다(§3.3의 역할 분담).

## 8. 검증

1. `npx tsc --noEmit` · `npm run lint` · `npm test`

5. **eval** — 전 16 시나리오 연속 2회 + 무난한 날 2종 5회. 새 검사(`⊆ items`)가 few-shot을 자기 검사로 통과하는지 포함
