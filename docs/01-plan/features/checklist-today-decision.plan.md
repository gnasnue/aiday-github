## 0. 제품 결정 (유효 — 변경 없음)

체크리스트는 **"오늘 달라진 것"**이다. 무난한 날은 0~1개다.

**근거:** 부모가 히어로에서 "물통만 챙기면 더 준비할 건 없어요"를 읽고 바로 아래에서 3개를 본다. 모델이 "물통만"이라고 쓰는 건 오작동이 아니라 정확한 판단이고, 모순은 "무난한 날도 최소 3개" 하한이 만든다. PR #173이 결정적 검사를 추가했으나 프롬프트로는 닫히지 않음을 4회 반복으로 확인(재채점 2건 → 3건 → 2~3건, 유의미한 감소 없음).

**조건 (대표 승인의 전제):** 지표 3번 정의를 같은 PR에서 함께 바꾼다. 0개 세션은 체크가 물리적으로 불가능한데 분모에 들어가 무난한 날 비율만큼 지표가 기계적으로 하락한다. 안 바꾸면 "정직해졌는데 지표가 떨어지니 되돌리자"는 오진으로 이어진다.

## 1. 왜 초안 설계를 폐기했나

초안은 `AI가 목록 생성 → 규칙 칩 별도 생성 → 런타임 합집합으로 모순 봉합` 구조였다. 외부 검증(Codex)이 이 구조의 전제 세 개를 깼고, **세 건 모두 코드로 확인했다.**

| 깨진 전제 | 검증 |
|---|---|
| 합집합이 `0~4개` 계약과 양립한다 | **거짓.** `lib/prep.ts:121` `.slice(0, 2)` × 슬롯 4개 = 최대 8개. 4개로 자르면 `칩 ⊆ 체크리스트`가 깨진다 — 두 불변식이 동시 만족 불가능 |
| `heroSt === "caution"`이 "오늘 경고 신호"를 뜻한다 | **거짓.** `issues` 후보는 강수·미세먼지·꽃가루·자외선·바람·습도뿐이고 **폭염·기온이 없다**(`lib/hero-brief.ts:374` 주석이 명시). 34°C 맑은 날은 `normal`이 되어 안전망이 안 걸린다. 게다가 첫 일정 슬롯만 본다 |
| 두 엔진이 무난한 날 모두 0개를 낸다 | **거짓.** `lib/prep.ts:104` `hasSkin && isPrimarySlot && !humid` → 피부 민감 아이는 날씨가 무난해도 보습제. 초안의 전제는 일반 아이에서만 검증됐다 |

Codex의 총평이 정확하다: **"모순을 제거하는 게 아니라 후처리 복잡도로 숨긴다."** 세 P0가 전부 "소스가 둘이라서" 생기는 문제다.

## 3. 새 방향 — 단일 결정적 소스

**형태:** 준비물 목록을 규칙 엔진 한 곳에서 만들고, AI는 그 목록을 **설명·우선순위화**한다.

**이 방향이 한꺼번에 해소하는 것:**

- `칩 ⊆ 체크리스트`가 자동 성립 (같은 소스)
- 상한 충돌 소멸 (한 곳에서 상한을 정한다)
- 무난한 날 0개가 확률이 아니라 결정 (프롬프트와 싸우지 않는다)
- eval의 예측력 회복 (API 출력이 곧 렌더 목록)
- 지표 계측이 결정적 입력에서 나온다

**이 방향의 근거는 이미 이 프로젝트 안에 있다.** 2026-07-20 제품 결정이 칩 엔진을 규칙으로 확정한 A/B 데이터: 커버리지 갭 규칙 0 vs AI 10, 결정성 규칙 0 vs AI 7슬롯 흔들림. "빠짐없이·흔들림 없이 보여야 하는 목록" 표면에서는 규칙이 이긴다는 증거다. 체크리스트도 같은 종류의 표면이다.

**대가:** AI 계약이 바뀐다(목록 생성 → 목록 설명). `hook`·`message`·`prepItems`·공유 카드·eval이 영향을 받는다. 초안보다 큰 작업이다.

**전환으로 해소되는 것**

**여전히 답해야 하는 것**

4. **`[]`의 정상/실패 구분 (P0)** — `route.ts:402` `Array.isArray(parsed.checklist) ? parsed.checklist : []`가 필드 누락·타입 오류를 정상 빈 목록으로 위장한다. 런타임 스키마 검증 + 실패는 폴백으로. (총 파싱 실패는 `hook === ""`로 잡히지만 필드 단위 실패는 안 잡힌다)
