- 최근 관련 변경: `#84`에서 UV·꽃가루를 AI 입력 관문 뒤에 연결했고, `#89`에서 SSE와 외부 요청 타임아웃을 추가했으며, `#94`에서 일부 로딩 잔상을 정리함.

## 검증된 사실

1. `uvP`·`pollenP` 완료 후 `setAiLoading(true)`가 호출되어 AI 캐시 확인과 생성이 늦어진다.
2. SSE는 완성된 `hook` 문자열을 추출한 뒤 첫 이벤트를 보낸다.
3. 당일 캐시는 `aiLoading`이 켜진 뒤에만 읽힌다.
4. `/auth/landing`과 `/home`이 프로필을 각각 조회한다.
5. `loading=false` 후 `aiLoading=true`가 되어 내용이 보였다가 스켈레톤으로 후퇴할 수 있다.

## 발견 사항

### T1 — P1: “home 도달”과 “AI 카드 안정”을 같은 지연으로 취급했다

AI 환경 조회는 `/home` 컴포넌트가 마운트된 후 `useEffect`에서 시작한다. 따라서 사용자가 실제로 `/auth/landing` 스피너에 5~10초 머무는 현상이라면 AI 워터폴은 원인이 될 수 없다. 현재 약 9초 계산은 **home 진입 후 첫 AI hook이 안정되는 시간**을 설명한다. 로그인 제출부터 URL 변경·home 첫 페인트까지의 운영 E2E 측정은 아직 없다.

**Before — 하나의 “로딩 시간”으로 취급**

```text
로그인 → home: 약 9초
```

**After — 성능 구간을 분리해 계측**

```text
auth_submit
→ auth_resolved
→ landing_profile_loaded
→ home_mounted
→ env_primary_ready
→ cache_hit | cache_miss
→ report_hook
→ report_done
```

**조치:** 수정 전 위 성능 마커를 추가하거나 운영 브라우저에서 동일 구간을 한 번 계측한다. 목표 지표도 `login_to_home_paint`와 `home_to_report_hook`으로 분리한다.

### T2 — P1: weather·air 도착 즉시 AI를 호출하고 UV·꽃가루 도착 후 재생성하면 비용과 일관성이 깨진다

Claude 제안 2번은 첫 생성에 UV·꽃가루를 누락한다. 이후 데이터를 반영하려면 같은 진입에서 Claude를 두 번 호출할 수 있고, 부모가 읽는 결론·체크리스트가 다시 바뀐다. 이는 현재의 “당일 고정 + 급변 때만 교체” 정책과 충돌한다.

**Before — 제안된 이중 생성 흐름**

```ts
await Promise.all([weatherP, airP]);
generateReport({ weather, air });
await Promise.all([uvP, pollenP]);
generateReport({ weather, air, uv, pollen });
```

**After — 느린 입력은 캐시·짧은 예산으로 해결하고 생성은 한 번만**

```ts
showCachedOrRuleReportImmediately();
const env = await getEnvironmentSnapshot({ staleWhileRevalidate: true });
await generateReportOnce(env);
```

**조치:** 클라이언트에서 AI를 먼저 호출하지 않는다. UV·꽃가루는 변동 주기가 길므로 마지막 정상값을 즉시 제공하는 서버 캐시 또는 통합 환경 스냅샷 API를 먼저 설계한다. 캐시 미스 때만 짧은 대기 예산 후 `null`로 한 번 생성한다.

### T3 — P1: “캐시 즉시 표시가 가장 큰 개선”은 캐시 히트 사용자에게만 맞다

캐시 키에 날짜가 포함되므로 같은 날 재방문·탭 이동에는 큰 효과가 있지만, 매일 첫 방문에는 항상 캐시 미스다. 서비스 핵심 사용이 “매일 아침 첫 리포트”라면 신규 일자의 9초 경로는 그대로 남는다. 현재 히트율 계측도 없다.

또한 `cur`는 동기적으로 존재해도 항상 최종 로그인 사용자의 프로필이라는 보장은 없다. `/auth/landing`을 거치면 DB 목록이 로컬에 저장되지만, 로그인 사용자가 `/home`에 직접 진입한 새 브라우저에서는 초기 데모/로컬 프로필이 DB 조회 후 교체될 수 있다. 잘못된 아이의 캐시가 잠깐 노출되지 않도록 프로필 준비 상태가 필요하다.

**Before — 네트워크 완료 후 캐시 확인**

```ts
if (!aiLoading || !cur) return;
const cached = JSON.parse(localStorage.getItem(cacheKey) ?? "null");
```

**After — 확정 프로필 기준 즉시 복원, 검증은 백그라운드**

```ts
const cached = readValidReportCache(confirmedProfile.id, localDateStr());
if (cached) showReport(cached);
void validateEnvironmentAndRefreshAtomically(cached);
```

**조치:** 1차 수정으로 채택하되 목표를 “같은 날 재방문 0초”로 한정한다. `cache_hit/cache_miss`를 기록하고, 확정 프로필 ID·스키마 검증·손상 JSON 방어를 포함한다. 재생성 중 기존 내용을 지우지 않고 완료된 결과를 원자적으로 교체한다.

### T4 — P1: 5.26초를 운영 모델 TTFB로 단정할 근거가 부족하다

측정 로그에는 `/api/report` 최초 개발 컴파일 803ms가 포함돼 있다. 또한 첫 SSE 이벤트는 모델의 첫 토큰이 아니라 완성된 `hook`의 닫는 따옴표가 도착한 시점이다. 서버리스 콜드 스타트, SDK 초기화, 게이트웨이 연결, 프롬프트 prefill, 모델 첫 토큰, hook 생성 시간이 합쳐진 값이다. 운영 `/api/report`를 동일 방식으로 직접 측정하지 않았으므로 “프로덕션 모델 또는 게이트웨이 5초”는 아직 가설이다.

`max_tokens: 1000`은 주로 전체 생성 길이 상한이며 첫 토큰 지연의 직접 원인으로 먼저 지목하기 어렵다. 반면 few-shot 3개를 포함한 입력 길이는 prefill에 영향을 줄 수 있다.

**Before — 단일 외부 지연으로 분류**

```text
Claude TTFB = 5.26초
```

**After — 서버 타이밍 분해**

```text
route_received
→ model_stream_requested
→ first_model_delta
→ hook_emitted
→ done
```

**조치:** 운영 환경에서 위 시점을 구조화 로그로 남기고, 동일 프롬프트로 기본 Anthropic 엔드포인트와 `ANTHROPIC_BASE_URL`을 각각 비교한다. 그 뒤에 모델·프롬프트·게이트웨이 최적화 여부를 결정한다.

### T5 — P1: 역방향 로딩 제거는 캐시 개선과 같은 묶음으로 먼저 처리해야 한다

현재 `loading=false`에서 규칙 기반 내용이 나타난 뒤 `aiLoading=true`로 다시 스켈레톤이 된다. 이는 첫 방문과 재방문 모두에 발생할 수 있어 캐시 히트율과 무관하게 체감을 훼손한다.

**Before — 기존 내용을 지우고 다시 로딩**

```ts
setAiLoading(true);
setAiHook("");
setAiMessage("");
```

**After — 기존 또는 규칙 기반 내용을 유지하고 백그라운드 갱신**

```ts
setReportStatus("refreshing");
// 기존 hook/message/checklist는 유지
const next = await generateReport();
replaceReportAtomically(next);
```

**조치:** 최초 콘텐츠가 나타난 뒤에는 카드 전체를 스켈레톤으로 되돌리지 않는다. 캐시가 있으면 캐시, 없으면 명시된 “기본 추천”을 유지하고 작은 갱신 상태만 표시한다. AI 결과는 `done`에서 한 번에 교체한다.

### T6 — P2: home의 프로필 조회는 단순 삭제하면 직접 진입 가드가 사라진다

중복 조회 자체는 사실이지만 `/home` 직접 진입, 다른 기기 로그인, DB 프로필 복원, 온보딩 미완료 가드 역할도 한다. `/auth/landing` 조회만 믿고 home 조회를 제거하면 해당 경로가 깨질 수 있다.

**Before — 매 진입 중복 조회**

```ts
// landing
await fetchProfilesFromDb();
router.replace("/home");

// home
await fetchProfilesFromDb();
```

**After — 공통 부트스트랩 결과 재사용**

```ts
const bootstrap = await getOrLoadProfileBootstrap();
// landing과 home이 같은 요청 결과/세션 캐시를 사용
```

**조치:** 단순 삭제가 아니라 인증·프로필 부트스트랩을 공통 provider/query cache 또는 서버 경계로 통합한다. 성능 영향이 작으므로 AI 로딩 안정화 뒤에 진행한다.

### T7 — P2: 문서의 캐시 버전이 코드와 불일치한다

코드는 `aiday:report:v12`를 사용하지만 `SPEC.md` 저장소 표와 API 설명 일부는 `v10` 및 구형 요청·응답 스키마를 유지한다. 이번 개선에서 캐시 스키마나 상태를 바꾸면 버전을 올리고 문서를 함께 맞춰야 한다.

**조치:** 구현 시 캐시 페이로드 변경 여부를 먼저 결정한다. 변경된다면 새 버전으로 올리고 `SPEC.md`의 키·`uv/pollen/prep` 스키마도 동시에 갱신한다.

## 수정된 실행 순서

1. **측정 경계 확정:** `login_to_home_paint`와 `home_to_report_hook`을 분리 계측한다.
2. **UI 안정화 + 캐시 즉시 복원:** 확정 프로필의 당일 캐시를 즉시 표시하고, 콘텐츠→스켈레톤 후퇴를 제거한다.
3. **첫 방문 경로 개선:** UV·꽃가루의 stale-while-revalidate 서버 캐시 또는 통합 환경 스냅샷으로 AI 생성을 한 번만 수행한다.
4. **운영 AI 타이밍 분해:** first delta와 hook 시점을 계측하고 게이트웨이/직접 호출을 비교한다.
5. **프로필 부트스트랩 통합:** direct `/home` 가드를 유지하면서 중복 조회를 제거한다.
