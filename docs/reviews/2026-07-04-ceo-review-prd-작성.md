## Step 0: Nuclear Scope Challenge

### 0A. Premise Challenge — 올바른 문제인가?

PRD가 통상 하는 일 4가지에 현재 문서를 대조하면:

| PRD의 역할 | 현재 상태 | 공백 여부 |
|---|---|---|
| 왜 만드는가 (문제·타겟·포지셔닝) | MANIFESTO.md가 담당 — 페인 정의, 포지셔닝 언어, 안티패턴까지 | 없음 |
| 무엇을 만드는가 (기능 요구사항) | SPEC.md v0.3이 담당 — 화면·필드 단위 명세 + 구현 현황 + 버그까지 코드 대조 완료 | 없음 |
| 어떻게 보이는가 (UX/디자인) | DESIGN.md가 담당 | 없음 |
| **성공을 어떻게 재는가 (지표·출시 기준)** | **어디에도 없음** | **있음** |

즉 "PRD가 없다"는 전제가 절반만 참이다. 통상적 PRD의 70~80%는 이미 MANIFESTO + SPEC으로 존재하고, 심지어 SPEC은 구현 현황과 동기화되어 있어 일반적인 PRD보다 신뢰도가 높다. **진짜 없는 것은 문서가 아니라 세 가지 '결정'이다:**

1. **성공 지표** — 무엇이 되면 이 MVP가 검증된 것인가 (예: 아침 재방문율, 리포트 체크리스트 완료율)
2. **출시 기준(Definition of Done)** — 어떤 상태가 되면 실사용자에게 공개하는가 (SPEC의 Phase 3~4 중 어디까지가 출시 차단선인지)
3. **보류된 제품 결정** — SPEC에 "미정의"로 남은 항목들: 게스트의 AI 리포트 호출 허용 여부(비용), /api/report 보호 방식, 데모 프로필 표기, 알림 1차 채널

아무것도 안 하면 무슨 일이 생기는가? — 개발은 SPEC Phase 3~4 순서대로 계속 굴러간다. 다만 "어디까지 하면 출시인가"를 정하지 않았으므로, Phase 4의 폴리싱(모든 숫자 실데이터화)이 끝없이 늘어질 위험이 있다. 이 위험은 풀 PRD가 아니라 위 3가지 결정만으로 막을 수 있다.

### 0B. Cheaper Alternative — 절반의 작업으로 같은 결과

풀 PRD(통상 10~20페이지: 배경·페르소나·유저스토리·기능명세·비기능요구·지표·마일스톤) 대신:

**2~3페이지 "제품 결정 문서" 1장** — 성공 지표(3개 이내) + 출시 기준(체크리스트) + 보류 결정 확정(4건). 기존 문서와 겹치는 부분은 전부 링크로 대체.

작업량은 풀 PRD의 1/4 이하, 커버하는 공백은 100%.

### 0C. Scope Cut — 잘라낼 것

작성하게 될 경우에도 다음은 **쓰지 않는다** (이미 있는 문서로 링크):

- 기능 상세 명세 → SPEC.md
- 문제 정의·타겟·포지셔닝·안티패턴 → MANIFESTO.md
- 화면 플로우·UI → SPEC.md + DESIGN.md
- 로드맵 서사 → README.md
- 페르소나·유저스토리 형식 채우기 — 1인 개발 + 사용자 검증 전 단계에서 형식적 산출물

## Step 1: 전략 정합성

- **MANIFESTO 원칙과의 정합**: "Decision First, Data Second"는 문서에도 적용된다 — 지금 필요한 건 요구사항의 재서술(Data)이 아니라 출시·비용·게스트 정책의 결정(Decision)이다.
- **MVP 단계 과투자 경계**: 사용자 검증 전이다. PRD는 팀 정렬 도구인데 현재 팀은 1인 + Claude 세션이고, Claude 세션들의 정렬 도구는 이미 CLAUDE.md → SPEC.md 라우팅으로 작동 중이다. 정렬해야 할 독자가 없는 문서는 유지비만 남긴다.
- **문서 드리프트 비용**: SPEC은 2회의 재감사(#35, #37)로 코드와 동기화를 유지해 왔다. 같은 내용을 담은 세 번째 문서(PRD)가 생기면 동기화 대상이 하나 더 늘어난다 — 이번 감사에서 README 기능 표가 이미 낡아 있음이 확인된 만큼 실재하는 비용이다.
- **기회비용**: 서비스의 핵심 약속("먼저 알려주는")인 알림 발송(N-01)이 미구현이고, Phase 3 잔여(프로필 포맷 정규화, /api/report 보호)가 열려 있다. 문서 작성 시간은 이 백로그와 직접 경쟁한다.
- **예외 조건**: PRD의 목적이 **외부 독자**(투자자 제출, 지원사업, 포트폴리오, 협업자 온보딩)라면 계산이 달라진다 — 그 경우 기존 문서를 재조립한 외부용 1장을 별도로 만드는 것이 맞고, 이는 본 판정과 별개의 요청으로 다룬다.

## Step 2: 판정 — **CUT**

**풀 PRD는 작성하지 않는다.** 통상 PRD 내용의 대부분이 MANIFESTO + SPEC + DESIGN으로 이미 존재하며, 중복 문서는 드리프트 비용만 추가한다.

**남길 최소 범위** (작성을 진행한다면 이것만):

`docs/PRODUCT-DECISIONS.md` 또는 SPEC.md 내 신규 섹션, 2~3페이지:

1. **성공 지표 3개 이내** — 예: (a) 온보딩 완료율, (b) 주 3회 이상 아침 재방문, (c) 체크리스트 인터랙션율. 측정 수단이 없으면 지표 옆에 "PostHog 연동 필요" 표기(Phase 5에 이미 있음)
2. **출시 기준 체크리스트** — SPEC Phase 3~4 항목 중 출시 차단(blocker)과 출시 후 개선(fast-follow)을 구분해 선 긋기. 최소 후보: /api/report 보호, 특이사항 매칭 버그, 약관·개인정보처리방침(아동 건강정보), 홈 목데이터 2종
3. **보류 결정 4건 확정** — 게스트 AI 호출 정책 / 데모 프로필 표기 / 알림 1차 채널 / localStorage 네임스페이스 통일

이 범위를 넘는 확장(페르소나, 유저스토리, 마일스톤 간트, 경쟁 분석)은 사용자 검증 이후로 미룬다.
