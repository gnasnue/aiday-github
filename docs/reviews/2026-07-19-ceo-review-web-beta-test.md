## 결론

2026-07-20부터 웹앱으로 베타테스트를 진행한다. 단, 공개 베타가 아니라 **초대된 6~15가구를 대상으로 한 7일 컨시어지 테스트**로 한정한다. 이번 테스트의 목적은 기능 수요 조사가 아니라 다음 세 가지 행동 가설을 검증하는 것이다.

1. 부모가 아침에 아이데이 브리핑을 반복해서 확인하는가.
2. 브리핑 때문에 옷차림·준비물·케어 행동을 실제로 바꾸는가.
3. 결과가 적절해 다른 날씨 앱으로 다시 확인할 필요가 줄어드는가.

자동 알림, 앱 전환, 커머스, 신규 콘텐츠 등은 이번 테스트 범위에서 제외한다. 사람이 매일 같은 시간에 링크를 보내는 수동 운영으로 선제성 가설을 검증한다.

## 시스템 감사

- 브랜치: `feature/beta-analytics` (`origin/main` 기준 작업 중)
- 미커밋 변경: 홈 리포트 평가, 마이페이지 자유 의견, 전역 행동 계측, 온보딩·가입·체크리스트 계측, `004_analytics.sql`
- 사용자 작업으로 보존한 기타 파일: `.claude/settings.local.json`, `.mcp.json`, 디자인 리뷰 문서 변경
- 최근 기준 커밋: 홈 하루 케어 플랜, AI 리포트 헤더, 프로필 칩, 자외선 시간대 오류, 온보딩 5단계 축소, 위치 기능 v1
- 자동 검증: Vitest 46개 통과, ESLint 통과, 프로덕션 빌드 통과
- 공개 데모: 랜딩과 게스트 홈 진입 성공, 약 8초 후 AI 리포트·체크리스트·시간대별 환경 표시 확인

### 즉시 발견된 문제

- `app/privacy/page.tsx`, `app/terms/page.tsx`는 정식 문서가 아니라 출시 예정 안내문이다. 아동 프로필·건강 특이사항·행동 로그를 수집하는 베타에는 부족하다.
- 계정 탈퇴와 계정 데이터 전체 삭제 흐름이 없다. 프로필 삭제만 가능하다.
- `/api/report`에 인증 또는 레이트리밋이 확인되지 않아 공개 URL에서 비용 남용 가능성이 있다.
- 베타 계측 변경이 미커밋·미배포 상태이고 `004_analytics.sql`의 원격 적용 여부도 확인되지 않았다.
- Google 가입은 `signup_completed` 분모에 포함되지 않아 가입→온보딩 퍼널이 왜곡된다.
- 저녁 결과 적합도, 다른 앱 재확인, 실제 행동 변화는 현재 인앱 이벤트만으로 측정할 수 없다.
- 공개 데모에는 현재 브랜치의 리포트 👍/👎와 자유 의견 기능이 아직 보이지 않는다.
- 기존 개발 서버와 프로덕션 빌드가 동일한 `.next`를 동시에 사용하면서 로컬 런타임/API 검증이 충돌했다. 배포 전 개발 서버 종료 후 깨끗한 빌드가 필요하다.

## Step 0 — Nuclear Scope Challenge

### 0A. Premise Challenge

올바른 문제는 “웹앱이 충분히 완성됐는가”가 아니다. **부모의 하루 첫 판단이 아이데이로 대체될 가능성이 있는가**이다. 테스트를 미루면 품질은 좋아질 수 있지만 실제 행동 가설을 더 빨리 배우지 못한다. 반대로 개인정보 고지와 최소 신뢰성 없이 시작하면 제품 가치보다 사고 대응만 학습하게 된다.

### 0B. Cheaper Alternative

- 자동 푸시 대신 매일 아침 카카오톡·문자로 동일 링크를 수동 발송한다.
- 저녁 결과 피드백 기능을 새로 만들기보다 1분짜리 폼으로 수집한다.
- 대규모 공개 모집 대신 이미 연락 가능한 6~15가구를 초대한다.
- 실시간 대시보드 대신 Supabase SQL 집계와 운영 스프레드시트로 매일 확인한다.

### 0C. Scope Cut

이번 베타에서 제외한다.

- PWA 설치와 웹 푸시 자동화
- iOS·Android 네이티브 앱
- 카카오 API 자동 발송
- 위젯, 공동육아, OCR, 커머스
- 건강팁 확장과 디자인 폴리싱
- 테스트 도중 P0 안전·데이터 오류가 아닌 기능 변경

## 테스트 시작 전 게이트

### 반드시 닫아야 하는 P0

1. 실제 개인정보 안내와 베타 동의: 수집 항목, 목적, 보유 기간, 삭제 방법, Supabase·AI 처리, 자유 의견에 개인정보를 쓰지 말라는 안내, 의료 진단이 아니라는 고지를 제공한다.
2. 배포 고정: 베타 브랜치를 한 버전으로 배포하고 7일 동안 실험 버전을 기록한다.
3. 계측 검증: `004_analytics.sql` 적용 후 익명·로그인 이벤트와 피드백 INSERT가 실제 적재되는지 테스트 계정으로 확인한다.
4. 비용·남용 보호: `/api/report`에 최소 레이트리밋 또는 초대 계정 제한을 둔다. 불가능하면 게스트 AI 호출을 닫고 로그인 테스터만 허용한다.
5. 데이터 복구: 가입→온보딩→로그아웃→재로그인 후 같은 프로필이 복원되고, 운영자가 삭제 요청을 당일 처리할 수 있어야 한다.
6. 운영 책임자와 중단 기준: 담당자, 문의 채널, 장애 기록표, 즉시 롤백 URL을 정한다.

### 내일까지 코드 대신 운영으로 대체 가능한 항목

- 자동 알림 → 수동 링크 발송
- 저녁 결과 기능 → 외부 1분 폼
- 인앱 계정 탈퇴 → 명시된 이메일 삭제 요청 + 24시간 내 수동 삭제
- 분석 대시보드 → 매일 정해진 SQL과 스프레드시트 집계

## 7일 실험 설계

- 표본: 이미 모집됐다면 12~15가구. 준비가 부족하면 6~8가구로 줄이고 공개 모집하지 않는다.
- 연령군: 만 1~2세, 3~6세, 7~8세를 구분하되 작은 표본의 백분율을 일반화하지 않는다.
- 기기: iOS Safari와 Android Chrome을 모두 포함하고 기기·OS·브라우저를 기록한다.
- 첫날: 20분 관찰형 첫 사용 테스트. 참가자가 소리 내어 생각하며 가입부터 첫 브리핑까지 진행한다.
- 매일 아침: 같은 시간에 링크 발송. 확인 여부, 브리핑 생성 성공, 소요 시간을 운영자가 기록한다.
- 매일 저녁: 실제 행동, 결과 적합도, 다른 앱 재확인 여부, 내일 수신 희망을 1분 폼으로 수집한다.
- 3일차: 중간 이탈자에게 원인만 확인하고 기능을 설득하지 않는다.
- 7일차: 20~30분 종료 인터뷰. 로그와 일기에서 보인 실제 행동을 기준으로 질문한다.
