## 결론

남은 4주의 목표를 **"공개 베타 완성"이 아니라 "안전한 폐쇄형 7일 컨시어지 실험으로 핵심 행동 가설을 판정"**으로 바꾼다.

이번 기간에 검증할 가설은 하나다.

> **부모가 아침에 아이 기준으로 해석된 브리핑을 받으면, 실제 준비 행동을 바꾸고 다음 아침에 다시 확인하는가?**

앱을 열기 전에 판단을 받는 경험은 **운영자가 매일 수동 발송한 링크/메시지**로 검증한다. 이 가설을 검증하는 데 자동 푸시, PWA, 카카오 연동, 전국 단위 지역화, 20~30개 Eval 완성, Family Memory는 필요하지 않다.

공개 공유·확산은 7일 실험의 결과와 안전성 검토 후에 다시 판정한다. 그 전에는 "공개 베타"라는 표현을 사용하지 않는다.

## Step 0: Nuclear Scope Challenge

### 0A. Premise Challenge — 지금 풀어야 할 문제는 무엇인가

지금의 문제는 기능 부족이 아니라 **"부모가 이 판단을 매일 실제로 사용하고 행동으로 옮기는가"라는 증거 부재**다. 사전 설문의 사용 의향은 방향성 근거일 뿐, 행동 증거가 아니다.

따라서 4주 동안 "알림을 자동화할 수 있는가", "전국 지역을 지원하는가", "장기 개인화 기반을 모두 쌓는가"를 해결해도 핵심 불확실성은 줄지 않는다. 반대로 같은 브리핑을 사람이 매일 보내고 사용자의 확인·체크·짧은 결과를 기록하면, 제품의 가장 위험한 가설을 직접 검증할 수 있다.

### 0B. Cheaper Alternative — 더 싼 검증 방식

자동 발송 파이프라인 대신 다음 운영 방식을 쓴다.

1. 참여자는 로그인한 뒤, 매일 아침 운영자가 동일한 당일 브리핑 링크/요약을 수동으로 한 번 발송한다.
2. 참여자는 홈에서 브리핑을 확인하고, 준비 체크리스트를 누르고, 저녁에 1문항만 답한다.
3. 운영자는 발송 여부·브리핑 조회·체크·저녁 응답을 최소 DB 레코드 또는 운영 시트로 확인한다.
4. 매일 안전·이상 출력만 운영자가 검토하고, 7일 후 짧은 인터뷰로 "무엇을 실제로 바꿨는지"를 확인한다.

이 방식은 "먼저 판단을 받는다"는 경험은 보존하고, 푸시 권한·Service Worker·VAPID·Cron·카카오 OAuth·토큰 갱신·중복발송을 모두 제거한다.

## 4주에 남길 최소 제품 (Must Ship)

### 1. 안전한 "한 번의 브리핑" 수직 슬라이스

- 로그인 사용자만 실제 AI 브리핑을 생성한다. 게스트는 정적 예시 브리핑만 보게 해 비용·어뷰즈 경로를 즉시 닫는다.
- 프로필 저장값을 코드로 정규화하고, 특이사항 매칭을 한 곳에서 해석한다.
- 위험 환경은 규칙이 먼저 판정하고, LLM은 안전한 행동 문장화만 맡긴다.
- 프롬프트의 약·질환 결과·치료를 암시하는 예시와 문구를 삭제한다. 출력 스키마·길이·금지 표현을 서버에서 검증하고, 실패하면 규칙 기반 안전 기본 브리핑을 보여준다.
- 실험 전 대표 고위험 10개(폭염·한파·고농도 미세먼지·꽃가루·자외선·비외출·데이터 누락·의료 유도 등)를 통과시키고, 매일 첫 생성 결과를 운영자가 확인한다.

### 2. 정직한 데이터 기준

- 테스트 지역을 한 곳으로 제한한다. 예: "서울시청 기상·종로구 대기질 기준"처럼 데이터 기준을 화면과 발송 메시지에 그대로 표시한다.
- "강남구" 같은 사실과 다른 지역명은 즉시 제거한다. 전체 지역 선택 UI·GPS는 만들지 않는다.
- 홈의 시간대별 환경을 기존 `hourlyForecast`에 연결해, 브리핑이 본 실제 근거를 사용자가 확인할 수 있게 한다.
- 새벽 발표 전 기상 데이터 fallback만 수정·테스트한다. 테스트 시간대의 빈 데이터는 신뢰 자체를 무너뜨린다.

### 3. 실험 운영에 꼭 필요한 최소 영속화·관찰

- `daily_briefings` 최소 테이블: 아이·날짜·입력 스냅샷·출력·fallback 여부·생성 시각. 아이당 하루 하나만 저장한다.
- 체크리스트 수용/해제와 저녁 결과 1문항만 저장한다. 자유 서술 수집은 하지 않는다.
- 발송 기록은 운영자가 남긴다. 자동 `notifications_log`·스케줄러는 지금 만들지 않는다.
- 실험 지표는 네 가지로 제한한다: 발송 성공, 아침 브리핑 확인, 체크리스트 1회 이상 실행, 저녁 적합도/짧은 인터뷰의 실제 행동 변화.

### 4. 폐쇄형 실험의 신뢰 경계

- 건강 특이사항은 코드형 선택지만 받고, 현재의 "기타" 자유 입력은 실험에서 숨기거나 비활성화한다.
- 참여 전에 수집 항목·사용 목적·철회/삭제 요청 경로를 명확히 고지하고, 민감정보 별도 동의를 받는다. 공개 베타 및 지속 운영 전에는 개인정보·약관 문안의 전문가 검토와 회원 탈퇴/연쇄 삭제를 완료한다.
- 이 범위는 **폐쇄형 지인 테스트**까지만 허용하는 운영 기준이다. 법적 검토가 끝나지 않은 상태의 공개 모집·공개 베타로 확대하지 않는다.

## Go / Iterate / Stop 기준

### Go — 자동화 투자를 검토할 신호

- 참여 가구의 절반 이상이 7일 중 3일 이상 아침 브리핑을 확인한다.
- 절반 이상이 최소 한 번 실제 준비물·옷차림·외출/실내 케어 결정을 바꿨다고 말한다.
- 안전 관련 심각 오류가 0건이고, "수정 없이 쓸 수 있다"는 응답이 다수다.
- 저녁 피드백과 인터뷰에서 반복되는 개인화 실패가 특정 규칙/입력 보강으로 설명된다.

이때도 먼저 할 일은 **브리핑 품질 보강과 최소 자동 알림 1채널의 작은 실험**이다. 카카오·야간·변화 감지 동시 구현이 아니다.

### Iterate — 가치 신호는 있으나 병목이 선명한 경우

- 브리핑은 보지만 체크하지 않는다 → 체크리스트를 더 적고 구체적인 준비 행동으로 재설계한다.
- 첫날만 보고 재방문하지 않는다 → 발송 시각·메시지 길이·일정 연동의 문제를 인터뷰로 분리한다.
- 특정 연령/환경에서만 신뢰가 낮다 → 해당 연령군 또는 리스크 규칙을 하나씩 보강한다.

### Stop / 재정의 — 더 만들기 전에 멈출 신호

- 수동으로 먼저 보내도 대부분이 확인하지 않거나, 확인해도 원래 날씨 앱을 다시 열어야 한다고 말한다.
- "내 아이 기준"보다 일반 날씨 요약으로 인식된다.
- 의료적 기대를 안전하게 관리할 수 없거나, 데이터 기준의 불신이 계속된다.

이 경우 알림 채널·앱 형태에 투자하지 않는다. 브리핑의 입력·결론·신뢰 표시부터 재정의한다.
