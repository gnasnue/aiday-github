# Engineering Plan Review — 아키텍처·기술 리뷰

계획 또는 현재 변경사항을 시니어 엔지니어 관점에서 검토한다. 질문은 하나다: **"이 설계가 깨지는 지점은 어디인가?"**

## 진행 순서

### 시스템 감사 (Pre-Review System Audit)
- 대상 파일과 각 파일의 역할을 표로 정리
- 변경 배경 요약 (선행 리뷰가 있으면 참조)

### 점검 항목
아이데이 코드베이스에서 반복적으로 문제가 된 영역을 반드시 확인한다:
- **에러 처리**: 외부 API 호출(`app/api/*` — 기상청·에어코리아·꽃가루·자외선·Claude) 주변 try/catch, 실패 시 사용자 피드백
- **중복 호출**: 같은 데이터를 여러 번 fetch하지 않는가 (홈 화면 날씨/대기 이중 호출 전례)
- **캐시**: 캐시 키 버전 규칙 준수 — 페이로드 스키마가 바뀌면 버전을 올려 구형 캐시 무효화
- **API 제약**: Anthropic API 파라미터 범위(temperature 0~1.0 등), 기상청 API 발행 시각(자외선 06시) 같은 외부 제약
- **타입/입력 방어**: `Number()` NaN 가드, 비정상 쿼리 파라미터 fallback
- **Next.js 15 App Router 호환성**: 서버/클라이언트 컴포넌트 경계, 스트리밍 제약

### Findings 형식
발견 사항은 `T1, T2, ...` 번호와 우선순위를 붙인다:
- **P0 (BLOCKER)** — 머지 불가
- **P1 (CRITICAL)** — 배포 전 수정 필수
- **P2 (MAJOR)** — 곧 수정
- **P3 (MINOR)** — 여유 있을 때

각 finding에 문제 설명과 Before/After 코드 스니펫을 포함한다.

## 산출물

리포트를 `docs/reviews/YYYY-MM-DD-eng-review-<주제>.md`로 저장한다. 서두 메타데이터 형식은 /plan-ceo-review 와 동일하다.

이 스킬은 리뷰만 한다 — 수정은 사용자 승인 후 별도로 진행한다.
